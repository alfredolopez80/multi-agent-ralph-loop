**Date**: 2026-08-28 · **Worker**: mmx-2 · **Machine**: this laptop

**Probe (permanent)**: `scripts/benchmark/hotpath_probe.py` — the same instrument that produced these numbers; will be re-run for the post-#48 before/after comparison. See [§ Reproduction](#reproduction).

## Scope and what is not measured

**Measured** (N=12 each, isolated HOME, synthetic stdin matching each event shape):

- 18 mechanisms spanning the named hot-path surfaces and a sample of the
  PostToolUse:Edit|Write|Bash chain. For each: median wall time, p90, max,
  min, plus the median token count of stdout.

**By construction** (asserted without measuring):

- `continuous-learning.sh` is called by `wake-up-layer-stack.sh` exactly
  once per SessionStart (grep confirms the only invoker). Per session: 1×.
- `learning-gate.sh` does not exist in `.claude/hooks/` (the only
  `*learn*` files are `continuous-learning.sh` and
  `orchestrator-auto-learn.sh`). The active learning surfaces are those
  two; the third, `orchestrator-auto-learn.sh`, only fires on
  PreToolUse:A|T (subagents), **not on ordinary Bash/Edit prompts**, so its
  hot-path cost on a plain session is 0 by construction.

**No-medible sin rediseño** (event semantics block synthetic measurement):

- SessionStart:* hooks (wake-up-layer-stack, project-state, vault-graduation,
  vault-promotion, auto-migrate-plan-state, auto-sync-global,
  session-start-restore-context, orchestrator-init, project-backup-metadata,
  session-start-repo-summary) self-background three of their internal jobs
  per T71's finding (wake-up-layer-stack v1.1.0). Their measured median wall
  time with isolated HOME is a warm-up cost; in production they fork off
  the heavy work and return. Reporting a single number would misrepresent
  the user's perceived latency. They are NOT in this table by design.

## Variant definition

The "hot path" for an ordinary user prompt = the union of:

- `PreToolUse:*` and `PreToolUse:Bash|Edit|Write|Agent|Task` hooks (fire
  synchronously before every tool call).
- `PostToolUse:*` and `PostToolUse:Edit|Write|Bash|Task|TaskUpdate|...`
  hooks (fire synchronously after every tool call).

`UserPromptSubmit`, `Stop`, `PreCompact`, `SessionStart:compact`,
`SessionEnd` are lifecycle events — measured separately because their
firing frequency per session is at most a handful, not N×tool-calls.

## Aggregates — what an ordinary Bash call costs

A single ordinary Bash call (synthetic `echo hello`) walks:

- **PreToolUse chain (Bash matcher)** = 186.2 + 79.3 + 26.3 + 21.8 + 6.7 ≈ **320 ms**
- **PostToolUse chain (Edit|Write|Bash matcher)** = 8.2 + 10.5 + 33.2 + 12.5 + 36.9 + 66.7 + 13.6 + 22.2 + 12.8 + 9.5 ≈ **226 ms**
- **Total per ordinary Bash call ≈ 546 ms of hook latency alone**, before
  the model/network/tool actually runs.

For an Edit (no git-safety-guard, no k8s-context-guard if k8s absent, but
permission-guard and repo-boundary-guard still apply):

- **PreToolUse chain (E|W matcher)** = 186.2 + 79.3 + 21.8 ≈ **287 ms**
- **PostToolUse chain (E|W|B matcher, but triggered by Edit)** = same 226 ms
- **Total per ordinary Edit call ≈ 513 ms**.

For a typical session (rough observation: ~10–30 tool calls per ordinary
user prompt; T74 measured similar magnitude), the per-prompt hook cost is
**~5–16 seconds** of synchronous latency. The T82 baseline measured 880 ms
of orchestration+state per Bash+turn on the FULL plane — consistent with
the 546 ms measured here plus the unmeasured-but-self-backgrounded
SessionStart:* hooks.

## The 5 numbers that weigh most for M2 (the decision lead needs)

1. **permission-guard = 186 ms / Bash call** (PreToolUse, fires on every
   Bash|Edit|Write|Agent|Task). Largest single contributor. It is a
   manifest control (#58 / T16+T19 hardening) — moving it async or batching
   it would unlock the most wall time, but it is the security plane's
   permission dispatcher; any rewrite is a security change, not an
   orchestration one. M2 must NOT touch this without a security review.

2. **status-auto-check = 67 ms / PostToolUse:E|W|B** (every Edit/Write/Bash).
   Output tokens ≈ 5 — it does NOT inject useful context. **Pure process
   overhead.** If the display is meant for the user only, it could move
   to async (the `quality-parallel-async.sh` pattern already exists).
   Candidate for retirement or async-ification with the lowest risk.

3. **k8s-context-guard = 26 ms / Bash call AND emits 3234 stdout tokens**
   when it fires (i.e. when the command line mentions kubectl). On a
   non-k8s session (this laptop), the same row is 26 ms but the **token
   injection is 0 for non-kubectl commands**. The 3234-token number is
   real on production k8s sessions. That token cost is hidden unless the
   user is on a cluster, and 3234 tokens of context per Bash call on
   k8s sessions is a material fraction of an 8K context budget.

4. **PostToolUse chain sum ≈ 226 ms / E|W|B**: dominated by
   status-auto-check (67), quality-parallel-async (37), plan-sync-post-step
   (33), ai-code-audit (22). Of these four, only `plan-sync-post-step` has
   clear write semantics (it patches plan-state on Edit); the other three
   produce display/state output. **3 of the top 4 PostToolUse hooks are
   display/state with ~5 stdout tokens each** — they exist to update
   side-files, not to inform the model.

5. **aristotle-analysis-display = 12.6 ms once per PreCompact**, not per
   tool call as the task framing suggested. PreCompact fires only when
   the model session is about to be compacted (a small number of times
   per long session). Its per-session aggregate is small; its per-fire
   cost is also small. **Already off the hot path by event semantics, no
   action needed for M2.**

## Findings beyond the numbers

- **The named "learning" mechanism (lead's three-item list) is already
  out of the hot path.** `orchestrator-auto-learn` only fires on
  PreToolUse:A|T (subagent spawns), `continuous-learning` fires 1×/session
  from the SessionStart hook. M2 doesn't need to act on learning for a
  plain prompt.

- **Six PostToolUse hooks emit only ~5 stdout tokens** (vault-fact-extractor,
  plan-sync-post-step, progress-tracker, quality-parallel-async,
  status-auto-check, console-log-detector, ai-code-audit,
  auto-format-prettier, session-accumulator — 9 of the 10 measured). That
  is too little to be context the model can use; it is side-file state.
  They could move to async without losing anything the user sees in the
  transcript.

- **`session-end-handoff` is the single heaviest per-fire cost (216 ms)**.
  It runs 1× per session. The M2 question is not whether to retire it
  but whether its work is currently cold-path-able (it writes to
  `~/.ralph/handoffs/`; that could be async).

- **The `audit-secrets.js` PostToolUse:* emits 0 stdout tokens** — it
  only logs. Already cheap (8.2 ms) and side-effect-only; a model would
  never notice if it ran 100 ms later.

## Reproduction

```bash
# 1. Bootstrap (one time, idempotent — creates scripts/benchmark/.venv)
scripts/benchmark/hotpath_probe.py --setup

# 2. Run the probe (N=12 per row, isolated HOME, ~one minute)
scripts/benchmark/hotpath_probe.py

# Optional flags:
#   --out <dir>    where to write hotpath-probe.{json,txt} (default: results/)
#   --runs <N>     runs per row (default 12)
#
# Outputs (results/ is gitignored, scripts/benchmark/.venv and
# .probe-home are gitignored):
#   results/hotpath-probe.json   — full per-row raw data (JSON)
#   results/hotpath-probe.txt    — markdown table (the one above)
#   scripts/benchmark/.venv/     — local venv with tiktoken (gitignored)
#   scripts/benchmark/.probe-home/ — isolated HOME used during the run
```

To re-run on a different machine or after hook changes, the probe needs
no modification — the hook list is the union of:

- Lead's named mechanisms (aristotle-analysis-display, learning,
  pre/post-compact, session-end).
- The hot-path PostToolUse:Edit|Write|Bash chain (9 hooks, all measured).
- A representative PreToolUse sample (security controls + Aristotle gate).

Adding a new hook: append a row to `TARGETS` in
`scripts/benchmark/hotpath_probe.py`.

## Probe as a permanent instrument

The harness is in the tree as `scripts/benchmark/hotpath_probe.py`
(decided mid-task: a one-shot probe in `results/` would have broken the
post-#48 before/after comparability — two different artifacts with
different N/payloads is not a comparison, it's two independent
measurements). Re-running the same probe on the same tree must produce
the same numbers within run-to-run variance; this is the property that
makes the certification matrix in `docs/benchmark/PLAN_CERT_METRICS.md`
mean something.

The differences from `scripts/benchmark_hook_planes.py`:

| Concern | benchmark_hook_planes.py | hotpath_probe.py |
|---|---|---|
| N | 5 | 12 (default) |
| Tokens measured | No (cites numbers) | Yes (tiktoken cl100k_base) |
| Scope | Both profiles, plane attribution | Hot-path mechanisms across planes |
| Plane map | Hardcoded | Inline `plane` field per target |
| Output | JSON + tables in scripts/ | JSON + markdown table in `results/` |
| Setup | stdlib only | stdlib + venv-local tiktoken (PEP 668) |
| Re-runnable for before/after | yes (single-profile) | yes (per-mechanism, cross-plane) |
